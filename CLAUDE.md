## Windows build environment (a different machine, not this one — set up 2026-09-12)

Getting a real `pio run` working on this specific Windows machine took working through five distinct, mostly-unrelated problems, in this order. **Do all of this before attempting a build in a new session/terminal on this machine** — several of these are per-shell-session state (env vars), not permanent fixes.

1. **Python version.** The system had only Python 3.14 (via the `py` launcher / Microsoft Store alias), but PlatformIO Core `6.1.19` refuses to run on anything newer than 3.13 (`ERROR: Python version must be 3.10, 3.11, 3.12, 3.13`). Installed Python 3.13 separately (via `winget`/the official installer) alongside the existing 3.14 — Windows' `py` launcher happily hosts both (`py -0p` lists all installed versions). Don't touch/uninstall the 3.14 install; other tools may depend on it.
2. **Always invoke `pio` via PlatformIO's own bundled virtualenv, never a separately-`pip install`ed copy.** `pip install platformio` under our own Python 3.13 works and even runs `pio --version` fine, but `pio run` crashes with `ImportError: cannot import name 'lfs' from partially initialized module 'littlefs'` — a compiled-extension ABI mismatch, because PlatformIO's `espressif32` platform script imports its own bundled `littlefs-python` from `~/.platformio/penv/Lib/site-packages`, which is compiled for **PlatformIO's own internal Python 3.11** (`~/.platformio/penv`), not whatever Python you used to `pip install` the `pio` CLI itself. The fix is simply to always run `pio` through `~/.platformio/penv/Scripts/pio.exe` (prepend `C:\Users\<user>\.platformio\penv\Scripts` to `PATH`) — this is the exact Windows equivalent of the Linux recipe's `export PATH="$HOME/.platformio/penv/bin:$PATH"`, just easy to miss since a bare `pip install platformio` also happens to produce a working-looking `pio` command.
3. **Console encoding crash + silent deadlock.** Partway through every build, a background thread reading PlatformIO's own subprocess output crashes with `UnicodeEncodeError: 'charmap' codec can't encode characters...` (Windows console defaults to cp1252; some build-log line contains a non-cp1252 character — seen right after the i18n build step prints non-English language names). Losing that reader thread means the child process's stdout pipe never gets drained, so the **whole build silently hangs forever** rather than failing loudly — `tasklist` will show `pio.exe`/`python.exe` still running long after the terminal looks idle. Fix: set `$env:PYTHONUTF8 = "1"` and `$env:PYTHONIOENCODING = "utf-8"` before running `pio`. If a build ever looks stuck with no new output for a while, check for this exception in the log and `taskkill /F /IM pio.exe /IM python.exe` before retrying.
4. **Never run `pio pkg install -e <env> ...` on this project.** It looked like a reasonable way to force-install a missing package (`tool-cmake`), but it **silently rewrote the entire tracked `platformio.ini`** — stripped every comment, collapsed formatting, added a generic boilerplate header. This is a real, committed project file; the rewrite would have destroyed a lot of curated documentation if it had been committed. Recovered with `git checkout -- platformio.ini`. If a package genuinely needs installing by hand, use the **global** form instead — `pio pkg install -g -t "platformio/<name>"` — which does not touch any project file.
5. **The real root cause behind several confusing failures: leaked `MSYSTEM`/MinGW environment variables.** Both the Bash tool (Git Bash) *and*, surprisingly, fresh PowerShell sessions on this machine inherit `MSYSTEM=MINGW64` and several `MINGW_*`/`MSYSTEM_*` variables (apparently set at the user/system environment-variable level, not just by Git Bash itself). ESP-IDF's own `idf_tools.py` (invoked by the `espressif32` platform to install `esptool`) explicitly detects and refuses to run under what it thinks is an MSYS/MinGW shell (`ERROR: MSys/Mingw is not supported`), which made `tool-esptoolpy` installation fail every single time — and that cascaded into a long, misleading detour (suspecting antivirus deleting `tool-cmake`'s files, which was never actually the real problem — turning off antivirus made no difference). The actual fix: clear these vars before every build:
   ```powershell
   Remove-Item Env:MSYSTEM,Env:MINGW_PREFIX,Env:MINGW_CHOST,Env:MSYSTEM_CARCH,Env:MSYSTEM_CHOST,Env:MSYSTEM_PREFIX,Env:MINGW_PACKAGE_PREFIX -ErrorAction SilentlyContinue
   ```

**Full known-good recipe, PowerShell, start to finish:**

### Fixes worth knowing the root cause of

- **Every Pokemon list screen was clipping its last row** (`95179ecc`, reported by the user as "the TM/HM row is missing" then corrected to "every menu screen is missing its last row, with a scrollbar now showing"): `buildList()`'s `screen.setContentMargin()` call computed its margin in raw-screen coordinates, but `Screen::setContentMargin()` insets from `frame_.safeRect()` (already shrunk by the device's 9px/3px top/bottom viewable margin) - so the margin got double-applied, silently shrinking the list's content rect by 12px below what `listBounds_` (`rowCount_ * rowHeight_`) promised, dropping exactly one row. Predates X4 Pro work entirely - traced to upstream's `v1.5.1-rc-6` merge (`414958d8`), which newly wired `safeArea` into that clamp; X3 was affected before any X4-Pro-specific change. Fixed by subtracting the same viewable margin back out in `buildList()`. Also fixed a related bug found while testing this: `scripts/dev/edit_pokemon_save.py`'s `add-party-member` bumped the save header's `recordCount` without updating the cached `payloadBytes` field, which `decodeSnapshotHeader()` independently checks on load - caused a real "save file corrupt" error (`a1089ade`).
- **Fainted Pokemon now require Revive/Max Revive** (`72ef328b`): `useConsumable()` previously let a plain Potion/Full Restore/status cure/PP restore quietly act on a fainted Pokemon (`currentHp == 0`). Fixed: those items now require `currentHp > 0` and return `NotApplicable` otherwise; only Revive/Max Revive (item ids 15/16) can act on a fainted one, restoring 50%/100% of max HP (their `effectValue` now read as a percentage for these two ids specifically) rather than curing status.
- **Wi-Fi OTA update pointed at the wrong repo** (`9952a2c5`): `pokemon-x3` never overrode `CROSSINK_OTA_RELEASE_URL`, so "Check for Update" silently pulled firmware from upstream `uxjulia/CrossInk` (matching asset name `firmware-x3-x4.bin`), which would flash a Pokemon-less build. Fixed by overriding the URL to this fork's own releases in that environment (and, since, in `pokemon-x4-pro` too).

### The Pokémon battle system (shipped `v0.2.0`, 2026-09-09, built on `feat/pokemon-battle-system`)

The full plan, technical constraints (flash budget, save-format append-only rules, the 48-byte `PokemonRecord` limit, i18n cost), design decisions with rationale, and a stage-by-stage task list (33+ stages, well beyond the original 8-stage roadmap, driven by real playtest feedback) all live in **[docs/development/pokemon-battle-roadmap.md](docs/development/pokemon-battle-roadmap.md)** — read that doc, not this section, for the detailed log. It covers: level-based move learning, items/TM/HM drops from reading, full turn-based battling with 6 status effects, catching with 4 ball types, 8 gyms + Elite Four in order, a Moveset management screen, switching mid-battle, using items mid-battle, and the Settings/Reset-Game screen (which also clears the auxiliary battle-data file so a reset game never inherits a previous playthrough's leftover HP/status).

**Constraints that are still load-bearing today** (i.e. still true post-v1.5.1-sync, still worth checking before touching save format or flash-sensitive code):
1. `PokemonState` can only be appended to **after byte 115** (`PokemonStore.cpp` hardcodes an offset for `sequence` before that point).
2. **Do not** widen `PokemonRecord` beyond 48 bytes — battle data (HP/PP/status/moveset) lives in a separate, double-buffered auxiliary file (`pokemon-battle-{a,b}.bin`).
3. Move/item names **do not** go through i18n (the per-language offset-table cost, and `gen_i18n.py --strip-unused` doesn't scan generated headers) — they're plain C strings in a generated header instead.
4. After editing anything under `lib/I18n/translations/*.yaml`, an incremental `pio run` can report "up to date" without actually rebuilding the generated i18n object — force a clean rebuild of that env before trusting behavior or flash numbers.
